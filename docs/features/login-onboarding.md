# Login & Onboarding

> Functional documentation — how the feature actually works, grounded in the real code on both platforms. For new developers and POs. Generated by `/document-projects`-style investigation on 2026-09-28; every claim is cited to its source file in `MyIsn.Android`/`MyIsn.iOS`.

## Purpose

Gets a returning or brand-new worker from "app just installed" to either their Home dashboard or, if they have no prior link to any company on ISNetworld, into the flow that connects them to their employer(s)/hiring clients (see [Connections](connections.md)). Also handles account-deletion "grace period" recovery, biometric unlock setup, and email verification troubleshooting.

## User journey

**Android** (`LoginViewModel.kt`, `GetStartedViewModel.kt`):
1. `GetStartedFragment` — user taps Sign Up / Login / "Trouble logging in."
2. Azure AD B2C (MSAL) flow runs. Cancel → back to Get Started. Error → "Login Failed" dialog. Success → `handleLoginSuccess`.
3. Token saved, profile fetched (force-refreshed only if there was previous cached user data), profile photo synced locally.
4. `processUserState(isNewUser)`:
   - **New user** → checks for a connection deep link first; otherwise tries to auto-match the user to existing ISNetworld/VMS records by phone+name and by email (parallel calls, VMS only if `VisitorManagementSystemFlag` is on).
     - Match found → **Connect Companies** screen.
     - Partial email match only → **Check Your Email** screen.
     - No match → **Enter ISN-ID** screen.
   - **Existing user** → checks for an active *cancelled* deletion request the user hasn't acknowledged → **Account Reactivation** screen if so; otherwise proceeds to biometrics gating.
5. Biometrics gating: if already enabled → Home. If not, a persisted "logins without biometrics" counter increments; **after 3 such logins**, the "enable biometrics" screen is shown once, then the counter resets. Constant: `MAXIMUM_LOGIN_WITHOUT_BIOMETRICS_ATTEMPTS = 3` (`ui/auth/LoginViewModel.kt`).

**iOS** (`WelcomeViewModel.swift`, `ProfileMatchViewModel.swift`, `EmailFoundViewModel.swift`, `BiometricsViewModel.swift`, `AccountReactivationViewModel.swift`):
1. `WelcomeView` — onboarding carousel (`build, scan, access, know, learn`, plus `visitor` if the VMS flag is on) with an embedded B2C webview for Sign up/Log in/Trouble logging in. Also checks the pasteboard for a deep-link code on first launch.
2. B2C success → `.profileMatch(newUser:)`.
3. `ProfileMatchViewModel` fetches profile + `AccountDeletionRequest` in parallel, then branches identically to Android: cancelled+unacknowledged deletion → Account Reactivation; deleted → reset to Welcome; new user → the same 3-way connection auto-match; existing user → biometrics check (`shouldDisplayEnableBiometrics()`, a `UserDefaults` counter resetting every 3rd login — login #1, #4, #7…).
4. "Check Your Email" (`EmailFoundViewModel`) — Skip goes to biometrics or root tab bar; "Enter ISN-ID" pushes that screen.
5. `AccountReactivationViewModel.updateDeleteRequest()` POSTs acknowledgement; success or "already gone" (404) both proceed to biometrics/tab bar.

## Business rules / validation

- **Login-without-biometrics counter**: Android counts logins *without* biometrics enabled specifically, resetting at 3. iOS's `timesLoggedIn` counts **every** login, also resetting at 3 — same cadence intent, different underlying event, so the two platforms can show the nag on different logins for the same usage pattern. **Worth a PO/eng alignment check.**
- **Account deletion/reactivation**: only a `CANCELLED` deletion status with `!userAcknowledgedCancellation` triggers reactivation. `INVALID_STATUS` fires an analytics event but otherwise proceeds as if there's no active request. A 404 on the deletion-request GET means "no active request," not an error — both platforms.
- **New vs. existing user** is driven entirely by `accessToken.isNewUser` from the B2C/MSAL token, not a separate app-side flag.
- **Deep link priority**: a connection deep-link token, if present, skips the auto-match step entirely (Android treats it as a manual ISN-ID entry later in Connections; iOS jumps straight to the tab bar after fetch).
- Android logs (but does **not** functionally handle) a specific MSAL "forgot password" error code — flagged as a possible gap, see Open Questions.

## Platform differences

- iOS folds Sign up/Log in/Trouble logging in into one `WelcomeView` with an embedded webview; Android uses a dedicated `LoginFragment` reached via 3 different nav actions.
- Android's biometrics-nag counter only increments while biometrics is *off*; iOS's counts every login regardless of biometrics state. Same 3-login cadence, different bookkeeping — can drift out of sync between platforms.
- iOS scans the pasteboard for a deep-link code on first launch; no equivalent was found in Android (Android's deep-link handling instead goes through `DynamicLinkController` inside `processUserState`).

## Key user-facing strings

- *"ISN-ID Already in Use"* / *"Someone else is already connected to this ISN-ID. Contact your admin if you think this is incorrect."*
- *"Tap the link in your email to get connected, or to manually connect, tap 'Enter ISN-ID'."*
- *"Login Expired — The session has expired or something went wrong. Please log in to continue."* (iOS)
- *"User Info Mismatch"* (both platforms, near-identical copy).

## Open questions for a PO

1. Does the product want a distinct in-app "forgot password" flow, or is MSAL's hosted reset page sufficient? Android currently only logs this case.
2. What does `AccountDeletionStatus.INVALID_STATUS` actually represent server-side? The app just logs an analytics event and proceeds as if nothing were pending.
3. Confirm whether the biometrics-nag cadence is meant to be identical across platforms — today it isn't, mechanically.
